The path tracer's GPU code is one TypeShade file, `trace.shade.ts`, with its sampler beside
it. The compiler emits it as WGSL, and the renderer runs it through the compiler's program
runtime, `typeshade/runtime`. The compiler can also run the same file on the CPU, as an
oracle. CI does both on every pull request.

## What CI holds

The harness renders the Cornell box at 16 by 16 pixels and 1024 samples a pixel in headless
Chromium on WebGPU, and again on the oracle, with the same kernel, seed and samples. It fails
when:

- two renders of one seed differ in any bit, or a second seed renders the same image.
- the mean relative difference between the GPU's image and the oracle's is over the bound.
- any channel of any pixel is further from the oracle's than the bound allows.
- the displayed image is not the tone map of the mean radiance.
- the site's example page does not render.

Each gate was shown to fail before it was trusted to pass: a 1% change to one albedo, a 1%
change to the exposure, a page that throws.

## Why the paths agree

A path depends on every decision it makes: where a ray lands, which way it bounces, whether
Russian roulette ends it. WGSL lets a GPU's `sin` and `cos` be off by 2^-11, which is enough
to send a ray past another edge. The kernel turns the bounce direction with a polynomial of
sums and products instead, which WGSL rounds correctly on every target, so the GPU and the
oracle take the same paths and differ only by f32 rounding.

The sampler is integer arithmetic, an Owen-scrambled Sobol sequence, so the GPU and the
oracle draw the same numbers for the same pixel, sample and dimension.

## The boundary

No package of the engine calls a WebGPU object. Every buffer, pipeline and dispatch goes
through `typeshade/runtime`, and `scripts/boundary.mjs` fails CI on an import past it. What
the runtime cannot do yet becomes a proposal to the compiler.
